# Repository Agent Guidance
本文件定义 AI agent 在本仓库中的长期工作约定。

## 工作方式

默认自主完成代码探索、实现、验证、repo intelligence 更新和临时文件清理。

仅在以下情况先询问用户：
- 存在会改变产品行为的多种合理方案。
- 需要作出难以逆转的架构决定。
- 需要显著扩大任务范围。
- 需要执行破坏性操作、写入外部系统或影响其他人员。
- 现有证据冲突，且无法由代码、测试或任务意图确定正确方向。
  
能够通过代码、测试、配置、文档或工具确认的事实，不要询问用户。
  
## 开始任务
  
开始代码任务前：
  
1. 阅读本文件和根目录 `CONTEXT.md`。
2. 根据任务范围，定向阅读相关的 `docs/modules/`、`docs/facts/` 与 `docs/adr/`。
3. 进入含有嵌套 `AGENTS.md` 的目录时，读取并遵守距离目标代码最近的规则。
4. 检查相关代码、测试、schema 和配置，确认文档描述仍然成立。
  
采用渐进式读取（progressive disclosure）：不要无差别加载全部知识文档，只读取当前任务所需部分。
  
## 实现与验证
  
修改前确认当前行为、期望行为、可验证的公共接口、不可破坏的约束，以及会受影响的具体模块。
  
优先修复根因，不以扩大条件分支、复制逻辑或增加隐式耦合来掩盖问题。
  
设计与重构时优先追求深模块（deep module）：用小而清晰的接口隐藏复杂性，集中不变量，减少调用方必须理解的内部细节。不要只为抽象而增加层级。
  
新增或改变行为时，尽可能先建立失败测试或其他稳定反馈信号；测试应验证公共接口的外部可观察行为，而不是实现细节。完成前运行与改动风险相匹配的测试、类型检查、lint 和其他验证。
  
诊断困难 bug 或性能问题时，先建立可重复的反馈回路；区分观察事实与待验证假设，一次验证一个关键假设。找到根因后，移除临时诊断代码和日志。
  
## Repo intelligence
  
Repo intelligence 是给未来开发者和 agent 使用的、当前仍然正确且可验证的项目知识；它不是聊天摘要、任务日志或历史档案。
  
```text
CONTEXT.md
docs/
├── adr/
├── facts/
├── modules/
└── work/
```

### `CONTEXT.md`
  
`CONTEXT.md` 只作为知识地图。它应包含：系统概览、核心领域术语、主要模块、最重要的事实、当前有效 ADR 的索引，以及常见任务的阅读指南。
  
不要将任务历史、调试过程、完整模块说明或不断增长的事实列表堆积到 `CONTEXT.md`。
  
### `docs/modules/`
  
记录值得单独理解的具体项目模块。它们不需要与源码目录一一对应；只有模块具有独立职责、稳定边界，且仅靠代码结构难以快速理解时才创建文档。
  
模块文档应按需说明：
  
- 对应源码位置。
- 目的、职责和非职责范围。
- 主要入口或公共接口。
- 依赖关系和关键流程。
- 必须维持的不变量与约束。
- 相关 facts 和 ADR。
  
### `docs/facts/`
  
按连贯的领域主题记录长期事实，例如领域规则（domain rules）、系统不变量（system invariants）、重要约束和跨模块行为约定。
  
只有同时满足下列条件的内容才进入这里：
  
- 长期有效。
- 会影响未来实现或判断。
- 不容易从单个代码文件直接得出。
- 可以指向证据。
  
每项事实提供稳定证据：源文件路径和符号、测试文件和测试名称、schema、迁移文件、配置、权威外部规范，或必要的验证命令。避免行号；它们容易失效。
  
不要记录当前失败测试数量、issue 状态、调试日志、未经验证的推测、临时 workaround，或已经被代码清楚表达的普通实现细节。
  
### `docs/adr/`
  
ADR 只记录具有长期影响且存在真实取舍的架构决定，例如跨模块边界、新系统边界、长期约束，或未来很可能被重新讨论的决定。
  
每份 ADR 至少包括：`Status`、`Context`、`Decision` 和 `Consequences`。
  
不要为局部实现选择、容易逆转的重构或代码风格创建 ADR。旧决定被替代时，保留其历史并标记 `Superseded`，再链接到新的 ADR；不要改写旧决定。
  
### `docs/work/`
  
这里只存放临时知识：当前 issue 状态、debug log、实验结果、临时 workaround 和未完成任务的交接信息。它不是长期事实来源。
  
任务完成前，将仍有长期价值的结论提升到 `docs/facts/`、`docs/modules/` 或 `docs/adr/`，再删除与任务有关的临时文件。Git 历史负责保存不再具有当前价值的过程信息。
  
## 知识正确性
  
长期知识不是只增不减的日志。系统变化时，更新、合并、替换或删除已经失效的知识；不要为了保留历史而让旧规则继续误导未来 agent。
  
当信息冲突时，按下列顺序调查：
  
1. 可重复的运行结果和自动化测试。
2. 当前实现、类型、schema 和配置。
3. 已接受且仍有效的 ADR。
4. `docs/facts/` 和 `docs/modules/`。
5. `CONTEXT.md`。
6. Issue、聊天记录和 `docs/work/`。

这不是“代码永远正确”的声明。必须判断是代码偏离设计，还是文档过期。能够确定时修正错误的一方；涉及产品或架构取舍时询问用户。不得在已知冲突未处理的情况下结束任务。
  
偶然发现与当前任务无关的过期知识时：能够低风险确认正确内容即可修正；无法确认或会显著扩大任务范围时，不要猜测。若仓库有 issue tracker，可建立范围明确的修复 issue；否则在最终回复中报告。
  
## Knowledge closeout
  
每个修改代码的任务，在结束前必须检查本次变更是否改变了：
  
- 架构决定。
- 模块职责。
- 领域规则。
- 系统不变量。
- 重要约束。
- `CONTEXT.md` 中的知识索引。
  
有变化时，在同一任务内更新相应的长期知识；没有变化时，不要为了留下工作记录而修改文档。
  
完成前确认：
  
- 临时诊断代码和日志已移除。
- `docs/work/` 的临时文件已完成知识提升并删除。
- 文档中的证据仍可定位。
- 新增文档已从适当的索引或相关文档链接。
- 代码、测试和知识文档之间不存在已知冲突。
  
最终回复中说明更新了哪些长期知识；若没有需要更新的内容，明确说明“无需更新 repo intelligence”。
  
## 文档语言
  
文档以中文为主。业界常用专业术语可保留英文，或在首次出现时添加英文注释。代码标识符、命令、文件路径和已有正式名称保持原样。
